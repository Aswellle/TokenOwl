# TokenOwl 技术架构与工程设计

## 1. 推荐技术栈

### Desktop

**Tauri 2 + React + TypeScript + Rust**。

选择原因：

- 桌面端资源占用通常低于 Electron 方案；
- Rust 适合网络并发、解析、定时调度、安全边界和本地数据层；
- React/TypeScript 适合高质量仪表盘与复杂交互；
- Tauri 2 已提供桌面和移动端能力，可让 Rust application core 具备未来移动复用路径；
- 官方 `create-tauri-app` 提供 React/TypeScript 模板；Tauri mobile 要求将共享 Rust logic 组织为 library crate，因此应从第一天按 shared core 设计。

参考：
- https://tauri.app/start/create-project/
- https://v2.tauri.app/zh-cn/start/migrate/from-tauri-1/

### Frontend

```text
React 19+
TypeScript 5+
Vite
pnpm
Zustand
TanStack Query（可选，用于 server-like async cache；核心状态仍由 domain event 驱动）
Framer Motion 或 Motion（只负责有限 UI motion）
CSS Variables + Tailwind CSS（用于 layout/utility，可搭配 CSS Modules）
Recharts / lightweight SVG charts（优先低成本 SVG）
Lucide React（图标）https://lobehub.com/zh/icons(AI/LLM相关图标在线网址)
```

### Rust


不要为一个桌面信息工具引入过度庞大的运行时。

## 4. 数据流

### 4.1 正常刷新

```text
Scheduler
  ↓
ProviderAccount
  ↓
CredentialResolver
  ↓
Provider Adapter
  ↓
HTTP Request / Local Source
  ↓
Raw Provider Response
  ↓
Parser
  ↓
Normalized QuotaSnapshot
  ↓
Validation
  ↓
SQLite Transaction
  ↓
Domain Event
  ↓
Tauri Event
  ↓
React Store
  ↓
Bubble + Dashboard
```

### 4.2 失败路径

```text
Provider request failed
        ↓
Classify Error
        ├── AUTH_REQUIRED
        ├── RATE_LIMITED
        ├── NETWORK_ERROR
        ├── PROVIDER_ERROR
        └── PARSER_ERROR
        ↓
Keep Last Known Good Snapshot
        ↓
Mark freshness/stale state
        ↓
Backoff & Retry
        ↓
UI continues normally
```

## 5. Scheduler

### 原则

不能让 30 个 Provider 每 60 秒同时请求。

每个 Provider 声明：

```text
min_interval
recommended_interval
retry_after_support
rate_limit_class
priority
refresh_on_open
refresh_in_background
```

调度器采用：

- priority queue；
- jitter；
- exponential backoff；
- retry-after；
- app foreground boost；
- idle slowdown；
- rate limit adaptive interval。

推荐默认策略：

```text
用户刚打开 Dashboard     → 立即刷新可见 provider
前台                     → 2–10 min（Provider 可覆盖）
后台                     → 10–30 min
刚发生 rate limit        → 遵循 Retry-After
连续失败                 → 5m → 15m → 30m → 1h
再次打开                  → stale 数据先显示，再异步刷新
```

## 6. Network Layer

统一 `HttpClient`：

- timeout；
- connect timeout；
- retry policy；
- `Retry-After`；
- TLS 默认强制；
- redirect policy；
- proxy support（系统代理 + 用户设置）；
- DNS error classification；
- response size limit；
- sensitive header redaction。

不允许 Provider 自己随意创建无限生命周期 HTTP client。

---

## 7. SQLite

SQLite 负责：

- Provider 配置；
- Account metadata；
- Quota snapshots；
- Usage points；
- Sync run；
- Notification history；
- App settings（非 secret）。

建议开启：

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
```

写入采用小事务；长时间网络任务绝不能占用数据库事务。

## 8. Credential Layer

所有：

- API Key
- OAuth Access Token
- Refresh Token
- Cookie
- Session Token
- Client Secret

必须进入 OS secure credential store。

Rust `keyring` 提供 macOS Keychain、Windows Credential Manager 等系统级存储封装；TokenOwl 只保存 `credential_ref`，SQLite 不保存 secret 明文。

参考：https://docs.rs/keyring/latest/keyring/

## 9. Tauri Window 架构

至少三个逻辑 Window：

```text
bubble
  → always-on-top / frameless / transparent

dashboard
  → dashboard panel / settings / history

onboarding
  → first-run / provider setup
```

可以通过同一个 Window 在不同尺寸间 morph，但为避免透明窗口和 WebView 布局边界问题，初期推荐：

- Bubble 为独立透明窗口；
- Dashboard 为独立 panel；
- Bubble 点击发送 `open-dashboard` event；
- Dashboard 关闭后 Bubble 保持存在。

后续再评估单窗口 morph。

## 10. 状态同步

前端不轮询 Provider。

Rust Scheduler 写入 snapshot 后发布：

```text
quota:updated
provider:status-changed
sync:started
sync:finished
```

React 只监听 domain events。

## 11. 性能约束

- UI 不渲染隐藏 Provider 的全部历史点。
- 大量 Provider 使用虚拟列表。
- Chart 默认只取时间范围内聚合数据。
- SVG/Canvas 仅在确有必要时使用。
- Bubble 禁止每秒 React 全树 re-render。
- countdown 使用单独轻量 timer，只更新秒数文本与必要 CSS。
- 网络任务永不运行在 UI 主线程。

## 12. 移动端预留

Rust Domain + Provider Protocol 必须做到 UI 无关。

移动端未来可以共享：

```text
packages/shared-types
Rust domain
Provider parser
Quota calculation
Storage abstraction
```

移动端 UI 单独实现：

```text
iOS / Android Dashboard
Widget
Notification
Background refresh
```

不要强行复用桌面的 Floating Bubble 交互。
