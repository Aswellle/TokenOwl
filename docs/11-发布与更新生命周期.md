# TokenOwl 发布与更新生命周期

本文描述 TokenOwl 的版本、GitHub Actions 发布、Tauri updater 资产和回滚边界。它是运维清单，不代表外部 GitHub 配置已经完成。

## 当前配置

- 应用版本的唯一编辑入口是根目录 `package.json` 的 `version`。
- `src-tauri/tauri.conf.json` 使用 `../package.json` 读取版本；`src-tauri/Cargo.toml` 保留同值作为 Rust 包元数据。
- `.github/workflows/ci-release.yml` 在每个 `vMAJOR.MINOR.PATCH` tag 上检查 package/Cargo 版本一致性，然后构建 Windows x86_64、macOS arm64 和 macOS x86_64。
- updater endpoint 是：
  `https://github.com/Aswellle/TokenOwl/releases/latest/download/latest.json`
- Tauri bundle 使用 `createUpdaterArtifacts: true`。`tauri-action` 使用签名资产生成并上传 `latest.json`。
- 仓库中只能出现公钥。私钥、私钥密码和 GitHub token 不得写入源码、日志、fixture、SQLite 或 release 文档。
- 运行时更新调用已实现：`updater_check`/`updater_install` 命令、`app:update-available` 事件与 UI 提示。GitHub secrets、签名 runner、Apple 签名/公证与端到端安装验证仍未完成。未完成这些外部配置和端到端验证前，不得对外声称“可发布”或“更新可用”。

## 通道

当前只支持 Stable 通道。`releases/latest/download/latest.json` 只应指向最新的非 draft、非 prerelease GitHub Release。

如果以后增加 Dev 通道，必须同时增加独立 endpoint、独立 GitHub prerelease 规则和独立签名密钥或明确的密钥兼容策略。Dev 资产不得成为 Stable endpoint 的 fallback；Stable 用户不能被静默切换到 Dev。

## 版本和 Tag

使用 SemVer `MAJOR.MINOR.PATCH`：

- MAJOR：不兼容的本地数据、配置或用户可见 API 变化。
- MINOR：向后兼容的新功能。
- PATCH：向后兼容的修复、文案或打包修复。
- 预发布版本可使用 `MAJOR.MINOR.PATCH-rc.N`，但当前 workflow 的稳定发布入口只接受 `vMAJOR.MINOR.PATCH`。

稳定 tag 必须严格为 `v1.2.3` 形式，并且等于 `package.json` 的版本。不要在 `tauri.conf.json` 或 Cargo 中另行 bump 一个不同版本。发布前：

1. 在 `package.json` 更新版本。
2. 确认 `src-tauri/Cargo.toml` 的 `version` 相同。
3. 确认变更日志、迁移说明、许可证和 release blockers 已审阅。
4. 提交并推送版本 commit。
5. 创建并推送对应 tag，例如 `git tag v0.1.0 && git push origin v0.1.0`。
6. 等待 `checks` 成功，再查看三个 release matrix job 和 GitHub Release 资产。
7. 人工下载 Windows、macOS arm64、macOS x86_64 资产，验证安装、启动、签名和 updater manifest 后再宣布稳定版本。

CI 会在 tag job 开始时失败，如果 package/Cargo 版本不一致、tag 不是严格 SemVer，或任何签名 secret 缺失。

## Update 行为

应用运行时应由 Tauri updater 在后台或用户手动操作时请求上述 HTTPS endpoint。没有新版本时不安装任何内容。发现更新后，UI 必须显示当前版本、目标版本、发布日期和 release notes，并由用户明确确认安装。

安装流程必须使用 Tauri 签名校验和原子替换：

1. 下载对应 target/arch 的 updater 资产。
2. 校验 `signature` 与内置公钥；失败时丢弃下载，不覆盖当前安装。
3. 在临时位置完成下载和校验，再执行安装。
4. 安装完成后提示用户重启；重启前保留当前运行会话。
5. 重启后重新打开本地数据库和 keychain，保留账户、快照和 provider 配置。
6. 更新检查、下载或安装失败必须显示可读错误，旧版本和最近快照继续可用。

运行时已注册 `tauri-plugin-updater`/`tauri-plugin-process`，并在 `src-tauri/src/lib.rs` 接入检查、用户确认、下载安装与 `app.restart()`；签名校验由 updater 使用内置公钥完成，失败时保留当前安装。UI 通过 `app:update-available` 事件显示可用版本。该流程尚未在真实签名 release 上端到端执行：不得把“CI 上传了 latest.json”或“代码已接线”当作验证通过。

## 数据库迁移和回滚

每个 release 都要说明 schema migration。迁移前检查 SQLite integrity，并创建可恢复的本地备份；迁移失败时保留旧 DB、进入 safe mode 或从备份恢复。更新器不能删除或重置 SQLite/keychain。

Updater 回滚分两类：

- 下载、签名或安装失败：Tauri 保留旧安装，用户可以重试；这是必须自动安全处理的路径。
- 新版本启动后发现数据或严重功能问题：停止该版本的 Stable 发布，标记 GitHub Release 为不可推荐，并发布修复的更高 PATCH 版本。不要复用同一个版本号或覆盖已经发布的资产。已安装版本需要通过正常签名更新回到修复版本；必要时提供文档化的手动旧版安装步骤。

GitHub Release assets 不自动删除。删除或替换资产会让旧版 updater manifest 的下载链接失效。

## 签名密钥

正式发布前必须生成并离线保存 Tauri updater 密钥对。私钥和密码只进入 GitHub Actions Secrets：

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`

公钥不是 secret：它是 `src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`，也就是每个构建内置的更新信任根。工作流在构建前检查两个私钥相关值非空，缺失时 fail closed，不创建未签名 Release；如果私钥与仓库公钥不匹配，签名资产无法被已验证的旧版本接受，轮换时必须按下面步骤发布。

密钥轮换步骤：

1. 生成新密钥并验证离线备份和密码。
2. 在受控环境用新私钥构建测试版本，确认新公钥能验证签名资产。
3. 更新 `src-tauri/tauri.conf.json` 中的 `plugins.updater.pubkey` 并同步 GitHub secret 里的私钥。
4. 发布一个更高版本，让已安装版本通过旧公钥更新到内置新公钥的版本；不要直接让旧版本读取新公钥签名的资产。
5. 保留旧私钥的离线封存，直到所有仍受支持版本完成迁移；不能把私钥提交到 Git。
6. 在 release notes 记录密钥轮换，不记录私钥或密码。

如果私钥或密码丢失，不能继续为已有安装签发可验证的 updater 资产。必须按产品支持策略发布重新安装路径；不能伪造签名或偷偷替换公钥。

## GitHub 权限和外部配置

在第一次真实 release 之前，仓库管理员必须完成以下项目：

1. 在 GitHub Actions repository secrets 中配置真实的 `TAURI_SIGNING_PRIVATE_KEY` 和 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`，并确认 `src-tauri/tauri.conf.json` 里的公钥来自同一密钥对。
2. 确认 Actions 的 workflow permissions 允许 `contents: write`；workflow 本身已声明该权限，但仓库级限制仍可能拒绝写 Release。
3. 确认允许 GitHub-hosted `windows-latest` 和 `macos-latest` runners，并接受对应的平台构建条款。
4. 确认仓库是 `Aswellle/TokenOwl`，tag push 能触发 `.github/workflows/ci-release.yml`，并且 Releases 允许 workflow 创建和上传资产。
5. 如果需要 macOS 分发签名或公证，另行配置 Apple Developer 证书、notarization credentials 和 runner secrets；本 workflow 不伪造这些凭据。
6. 先运行一次只验证 checks 的 pull request，再使用测试签名密钥完成 draft/内部 release 验证。不要用真实账户凭据测试。
7. 配置 release reviewer、tag protection 和 secret 管理权限，避免任意 pull request 读取或修改生产签名环境。
8. 发布前确认 updater runtime plugin 已注册、权限已生效，并在至少一台 Windows 和两种 macOS 架构上验证检查、签名失败、安装、重启、数据保留和回滚说明。

在以上项目未完成时，正确状态是“release foundation configured, publishing blocked”，而不是 release ready。

## Release Blockers

任何一项存在都必须停止发布：

- checks、构建、安装或启动失败；
- package/Cargo 版本不一致或 tag 不符合规则；
- 任一签名 secret 缺失、错误或无法验证；
- 私钥进入 Git、日志、fixture、artifact 或普通 issue；
- `latest.json` 缺少目标架构、URL 或 signature；
- updater endpoint 不是 HTTPS 或指向错误仓库；
- 数据库迁移没有备份、完整性检查或恢复路径；
- 更新失败会覆盖旧版本、删除 SQLite/keychain 或无法回到可用版本；
- 未完成 Windows/macOS 安装、签名、更新和重启验证；
- GitHub token 没有 `contents: write`，或 workflow 无法创建/更新 Release；
- Apple 签名/公证是产品分发要求但尚未配置；
- 仍存在会把未知额度显示为精确值、泄露 secret 或隐藏 stale/error 状态的已知问题。
